# AlinaCoder — Critical Intelligence Audit of v0.1

Date: 2026-09-04  
Target: `docs/superpowers/specs/2026-09-04-alinacoder-v0.1-design.md`  
Decision: evolve to v0.2 while preserving full autonomy and direct-to-`main` operation.

## Executive verdict

The v0.1 specification is a strong execution and safety skeleton, but it is not yet an adequate intelligence architecture for the ambition of AlinaCoder.

Its strongest parts are deterministic guardrails, checkpoints, resumability, explicit Done Contracts, direct execution evidence, and a deliberately modular Python architecture. Its weakest parts are the cognitive layer and repository intelligence layer: `planner.py`, a generic “project map”, SQLite memory, and test discovery are underspecified for large repositories, cross-file reasoning, causal debugging, architectural impact analysis, regression prevention, and learning from project history.

The main v0.2 recommendation is **not** to add a complex multi-agent system. AlinaCoder should keep one Ollama model and one deterministic orchestrator, but surround that model with better representations and decision processes: structure-aware repository intelligence, dependency/test-impact analysis, hierarchical adaptive planning, evidence-grounded hypothesis testing, a critical decision gate, artifact-anchored verification memory, and validated lessons from failures/history.

This retains the simplicity and inspectability of the original design while substantially increasing effective reasoning quality.

## Critical gaps

### P0-1 — Repository intelligence is too flat

The v0.1 “project map” lists structure, manifests and important files, but it does not define a machine-queryable representation of relationships. Large-project reasoning needs at least typed edges for containment, imports, calls, inheritance, public interfaces, build/config dependencies, source-to-test relationships, and optionally data-flow slices.

**v0.2 change:** introduce an incremental Repository Intelligence Graph with lightweight global indexing plus on-demand local expansion. Avoid a heavyweight graph database by default.

### P0-2 — No explicit change-impact model

v0.1 can run targeted and broad tests, but it has no deterministic answer to “what can this patch break?”. That makes regressions either expensive to detect (run everything) or easy to miss (run nearby tests only).

**v0.2 change:** add pre-change and post-change impact analysis over dependency/test edges. For every changed symbol/file, compute direct and transitive affected components and an impacted-test set. Regression testing becomes evidence-driven.

### P0-3 — No baseline/pass-to-pass contract

A test that is green after a patch is not useful evidence if it was already broken before the task. Conversely, previously green tests that turn red are the clearest regression signal.

**v0.2 change:** when practical, establish a scoped pre-change baseline for impacted tests and maintain explicit fail-to-pass / pass-to-pass outcomes.

### P0-4 — Planning and memory are independent

v0.1 has a planner and memory but no contract saying that plan phase controls retrieval or that repeated failures in memory force replanning. This permits stale plans and repeated dead ends.

**v0.2 change:** hierarchical plan state and episodic memory become bidirectionally coupled. Plan phase filters relevant memory; memory-derived stagnation and contradiction signals can invalidate assumptions and trigger replanning.

### P0-5 — Debugging is correction-first rather than hypothesis-first

The current `failure → diagnostic → hypothesis → correction` loop is a good start but too informal. A single plausible explanation can become an anchoring bias.

**v0.2 change:** formal Hypothesis Ledger. For nontrivial failures, generate multiple plausible root-cause hypotheses, record supporting/contradicting evidence, define a falsification probe, rank hypotheses, and edit only when evidence crosses a configurable threshold or one minimal diagnostic patch is justified.

### P0-6 — No reproduction gate

The agent can start changing code before it has demonstrated the defect or defined the behavior to preserve.

**v0.2 change:** bugs should attempt to construct or identify a deterministic reproduction before implementation. If reproduction is impossible, AlinaCoder must explicitly record why and use a weaker verification class rather than pretending equivalent confidence.

### P0-7 — Memory has no provenance or freshness model

SQLite entries can become stale after files change. v0.1 says reality wins, but it does not specify how individual claims become invalid.

**v0.2 change:** every durable technical claim carries provenance, evidence type, artifact anchors/content hashes, confidence class, created-at commit, and freshness. A changed anchor marks the claim `STALE`; missing replacement evidence marks it `UNPROVABLE` rather than guessed.

### P0-8 — No validated lesson-learning pipeline

Recording failures is not the same as learning. Raw failure history can pollute future decisions.

**v0.2 change:** separate `episode` from `lesson`. Failed/successful attempts create candidate lessons; only lessons supported by execution evidence and a quality gate are promoted. Lessons must record applicability conditions and invalidation anchors.

### P0-9 — Project Git history is unused intelligence

Past commits contain repository-specific conventions, co-change patterns, previous bug fixes, migrations, and architectural intent.

**v0.2 change:** build a lightweight History Intelligence layer from `git log`, `git show`, `git blame`, commit messages, co-change statistics and prior diffs. Retrieval is task-directed, not a dump of history into context.

### P0-10 — Single-path design selection encourages plausible-but-fragile patches

v0.1 asks the planner for a plan and then executes it. For nontrivial changes, a locally plausible design can be architecturally wrong.

**v0.2 change:** before medium/high-risk changes, generate 2–3 candidate solution designs using the same Ollama model in isolated passes. Score them on correctness evidence, scope, simplicity, dependency impact, architectural fit, testability, reversibility, maintenance cost, and regression risk. Pick the simplest robust solution, not the cleverest solution.

### P0-11 — Reviewer correlation is under-addressed

The same model plans, codes and reviews. A fresh prompt helps, but correlated blind spots remain.

**v0.2 change:** keep the single-model decision, but make the critic evidence-driven and context-isolated. The critic receives requirement, assumptions, dependency/impact evidence, patch, test evidence, and must search specifically for counterexamples. It cannot override deterministic failures.

### P0-12 — No best-known-state optimization

Rollback returns to a checkpoint, but v0.1 does not define how to choose among multiple partially successful attempts.

**v0.2 change:** maintain a `BestKnownState` scored by behavioral reproduction, regression count, test pass vector, static checks, diff risk and unresolved invariants. Recovery may revert to the best state, not merely the most recent one.

## Important P1 improvements

### P1-1 — Active context management

Replace passive “compression after long runs” with an explicit context manager containing:

- immutable task/requirement anchors;
- current plan and assumptions;
- short-term recent observations;
- compact reasoning digests;
- retrieved evidence packets;
- durable episodic memory references.

Condensation should happen at phase boundaries and budget pressure, preserving paths, symbols, failing tests, decisions, unresolved hypotheses and changed interfaces.

### P1-2 — Intent-aware hybrid retrieval

Do not rely on embeddings alone and do not require embeddings in v0.2. Combine:

1. lexical search (`rg`/symbol lookup),
2. structural graph traversal,
3. test-impact relations,
4. Git/history evidence,
5. runtime traces/logs.

Retrieval strategy should depend on intent: architecture question, bug localization, API change, test failure, feature addition, or regression investigation.

### P1-3 — Transitive closure must be explicit

Graph availability does not guarantee correct reasoning. Impact questions must explicitly compute bounded or full transitive closures rather than trusting the model to stop at the right hop depth.

### P1-4 — Runtime evidence beyond exit codes

For difficult bugs, support targeted instrumentation and concise telemetry: traceback frames, assertion deltas, selected variable values, timings, and call-path evidence. Instrumentation must be temporary, traceable and removed before commit unless intentionally retained.

### P1-5 — Test adequacy, not only test count

For high-risk code where passing tests provide weak assurance, support optional selective mutation testing, property tests, contract checks, or differential tests. These are escalations, not mandatory for every task.

### P1-6 — Public-interface and architectural invariant detection

Track public signatures, exported symbols, config schemas, dependency declarations and key architecture rules. A patch that changes an interface must explicitly identify and validate downstream consumers.

### P1-7 — Atomic edit primitive

Do not make PowerShell the only mutation mechanism. Add a deterministic patch/edit tool with pre-image content hash, unique-match replacement/unified diff application, atomic write, post-write syntax parse where available, and stale-file rejection.

### P1-8 — External drift detection

Before every write/commit, verify that files and HEAD still match the state used to plan the action. Reconcile/replan if another process changed them.

### P1-9 — Model selection based on actual capability probes

Metadata such as model name/size is insufficient. `doctor` should optionally run small local probes for structured-output compliance, code-edit ability, context use and tool instruction following, then combine probe quality with memory/VRAM constraints.

### P1-10 — Autonomous self-improvement needs a locked evaluator

Self-modification should be measured against a fixed local acceptance/evaluation suite. Evaluation scripts and baselines must be integrity-protected. A self-improvement is promoted only when composite quality improves without violating regression/safety floors.

## Simplicity rules retained from v0.1

The research audit strongly warns against equating architecture size with intelligence. The following constraints are therefore deliberate:

1. **One Ollama model remains the default and only model in v0.2.**
2. Logical roles (planner, critic, debugger) are prompt/context modes, not concurrent LLM agents.
3. No mandatory vector database.
4. No mandatory graph database; start with in-process/incremental structures and serialized caches.
5. No event-distributed architecture.
6. No hundreds of bespoke tools; prefer a small, high-value tool surface.
7. No verbose ritualized prompting when structural evidence can answer the question.
8. No refactor unless required by the task or measurable architecture debt blocks a robust solution.
9. Prefer minimal patch surface and stable public interfaces.
10. All GitHub development remains on `main`; v0.2 does not introduce branches or PRs.

This is consistent with the practitioner signal from mini-swe-agent: very small agent scaffolds can be highly competitive, so intelligence should be invested in context quality, evidence and execution rather than framework ceremony.

## Proposed v0.2 cognitive loop

`Reconcile → Understand → Localize → Hypothesize → Plan → Compare → Act → Reproduce/Verify → Impact/Regression → Critique → Commit → Learn → Next`

The loop is adaptive. Low-risk mechanical actions may skip hypothesis comparison. Medium/high-risk changes must use deeper deliberation and stronger verification.

## Decision quality contract

Before a nontrivial code change, AlinaCoder should know:

- What observable behavior is required?
- What is currently true, and which evidence proves it?
- Which assumptions remain uncertain?
- Which modules/symbols/tests are affected directly and transitively?
- What are at least two plausible solutions when architectural choice exists?
- Which solution minimizes complexity while satisfying requirements?
- What could regress?
- What evidence will falsify the chosen approach?
- What is the rollback/best-known state?

If these cannot yet be answered, the next action should usually gather evidence rather than edit code.

## Memory quality contract

Durable memory is partitioned into:

- `facts`: evidence-backed project facts;
- `decisions`: architectural/product choices plus rationale;
- `episodes`: attempts and outcomes;
- `lessons`: validated reusable conclusions;
- `invariants`: contracts that should remain true;
- `history_patterns`: repository-specific patterns distilled from Git;
- `verification_claims`: claims anchored to artifacts/tests.

Each record carries source/provenance, commit/version context, confidence/evidence class, freshness, and optional invalidation anchors.

## Regression quality contract

For every patch, AlinaCoder classifies change risk and builds a verification envelope:

1. task-specific fail-to-pass or acceptance checks;
2. impacted pass-to-pass regression checks;
3. static/type/lint/build checks relevant to the changed dependency closure;
4. public-interface/invariant checks;
5. optional stronger adequacy checks for high-risk changes.

A patch is not promotable if newly broken previously-passing checks remain unexplained.

## Autonomy invariant

v0.2 maintains full autonomy:

- AlinaCoder may choose work autonomously.
- It may investigate, modify, test, recover, commit and push autonomously.
- It works directly on `main`.
- No approval is required for ordinary successful tasks.
- It asks for a human decision only when a requirement is genuinely underdetermined and cannot be safely resolved from repository evidence/configuration.

More intelligence must reduce unnecessary human intervention, not increase it.

## v0.2 acceptance metrics

In addition to v0.1 success criteria, implementation should expose measurable quality metrics:

- localization precision/recall on known fixtures;
- dependency/impact-map correctness;
- impacted-test recall;
- fail-to-pass success rate;
- pass-to-pass regression count/rate;
- repeated-failed-action rate;
- recovery-to-best-state success;
- plan revision count with cause;
- stale-memory detection accuracy on fixtures;
- lesson reuse success / invalid lesson rejection;
- context/tool-call efficiency;
- unnecessary diff size / files touched;
- public-interface regression count;
- self-improvement benchmark delta with safety/regression floors.

## Final audit conclusion

The v0.1 design should not be discarded. Its deterministic orchestrator, safety policy, Git checkpoints, CLI, Ollama-only constraint, continuous autonomous loop and evidence-over-model principle are the correct foundation.

v0.2 should add intelligence primarily through **better state representations and better evidence discipline**:

- a repository/architecture/dependency graph;
- impact-aware regression testing;
- hierarchical plan-memory coupling;
- multiple falsifiable debugging hypotheses;
- alternative-design comparison with a simplicity prior;
- structured historical/episodic learning;
- artifact-anchored memory freshness;
- runtime telemetry and best-known-state recovery;
- active context management;
- locked empirical evaluation for self-improvement.

This produces a substantially more capable agent while preserving the most important engineering lesson from current coding-agent practice: **keep the control loop understandable, and make the information flowing through it much better.**
