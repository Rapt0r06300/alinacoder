# AlinaCoder v0.2 Self-Healing Installer Design

## Goal

`AlinaCoderSetup.exe` must autonomously diagnose, repair, resume, and complete a full AlinaCoder installation on supported Windows 10/11 systems whenever the failure is safely recoverable. A failed attempt must never destroy a previously healthy AlinaCoder installation or weaken provenance/security checks.

## Non-negotiable invariants

1. **Fail-safe, not fail-open.** SHA-256, allow-list, Authenticode, minimum-version and smoke-inference failures are never bypassed.
2. **Preserve the last healthy application.** A new `AlinaCoder.exe` is staged and verified before promotion. Existing working binaries remain untouched if staging or promotion fails.
3. **Atomic application promotion.** Application replacement occurs from a sibling staging file with backup/restore protection and same-filesystem `os.replace` semantics.
4. **Idempotent repair.** Re-running setup after interruption, partial extraction, stale cache, missing prerequisites, or an incomplete bootstrap converges toward one healthy state.
5. **Automatic recovery.** Recoverable failures trigger diagnosis, remediation and bounded retry without requiring the user to press Retry.
6. **No infinite loops.** Default policy is 4 complete attempts with exponential backoff. Fatal/security errors stop immediately. A bounded environment override may raise the attempt count for diagnostics.
7. **Durable evidence.** Each attempt writes an atomic recovery journal describing attempt number, classification, remediation, completion state and last error.
8. **User data safety.** Recovery may clean only AlinaCoder-owned transient/staging/cache paths. It never purges user data or pre-existing third-party installations.
9. **No forced reboot.** Exit code 3010 is treated as a successful prerequisite installer result, but setup must verify the observable installed state before declaring readiness.
10. **Full-install gate.** Success means: application binary promoted and verified; prerequisite bootstrap ready; selected model present; Ollama healthy; real model smoke test succeeded; install metadata reports ready.

## Existing strengths retained

The current v0.2 implementation already provides official GitHub release allow-lists, SHA-256 verification, Authenticode validation, MinGit staging/rollback, resumable Ollama pulls, bootstrap receipts, managed prerequisite provenance and Windows filesystem retries. The self-healing layer must compose those mechanisms instead of replacing them.

## Architecture

### 1. `recovery.py`: diagnosis and policy

Add a small UI-neutral recovery module with:

- `RecoveryPolicy`: maximum attempts and bounded exponential backoff.
- `RecoveryDecision`: failure category, recoverable/fatal decision and safe remediation list.
- `RecoveryJournal`: atomically persisted attempt/evidence state.
- `classify_failure(exc)`: conservative classifier.
- `cleanup_transients(install_dir)`: removes only known AlinaCoder transient files/directories such as `*.partial`, app staging/backup remnants that are not the active target, MinGit staging remnants, and malformed cache entries.

Recoverable classes include transient network/timeout errors, `PermissionError`/sharing violations at owned staging/cache boundaries, incomplete bootstrap reports, model-pull failure and missing/corrupt transient downloads. Provenance allow-list failures and repeated Authenticode failures are fatal and remain fail-closed.

### 2. Transactional application binary promotion

Replace direct `shutil.copy2(source, target)` with a helper that:

1. copies source to `AlinaCoder.exe.staging`;
2. fsyncs the staged file where supported;
3. verifies staged SHA-256 equals source SHA-256 and staged size is non-zero;
4. copies the existing target to `AlinaCoder.exe.backup` if present;
5. promotes staging with `os.replace`;
6. verifies the promoted target hash;
7. restores the backup if post-promotion verification fails;
8. removes backup only after the complete install gate is healthy.

If promotion fails because the target is locked, the existing target is preserved. Recovery retries with bounded backoff rather than truncating the active executable.

### 3. Self-healing operation runner

Add `run_self_healing_operation(...)` in the installer boundary. Each attempt:

1. writes `recovery-state.json` with `running` state;
2. cleans safe transients;
3. runs install/upgrade/repair through the existing bootstrapper;
4. validates the full-install gate;
5. commits application backup cleanup and journal `ready=true` on success.

On failure it classifies the exception, records evidence, performs only the mapped safe remediation, sleeps according to policy and retries when recoverable. Fatal failures immediately stop while preserving the previous healthy app.

### 4. Visible setup controller

`SetupController._default_operation` uses the self-healing runner. Recovery attempts emit visible `repair` / `retry` events so the user sees what AlinaCoder is diagnosing and fixing. Manual `Retry` remains available only after automatic recovery is exhausted or cancelled.

### 5. CLI parity

Default install, explicit `--repair`, and explicit `--upgrade` use the same recovery runner. `--rollback`, `--uninstall`, and `--bootstrap-only` preserve their current semantics.

## Failure classification

| Failure | Default action |
| --- | --- |
| `TimeoutError`, `urllib.error.URLError`, transient `OSError` during download | clean `.partial`, backoff, retry |
| SHA mismatch from an official allow-listed asset | delete transient/cached affected payload, re-resolve once, retry |
| Authenticode invalid | delete payload, fail closed after one fresh verification; never bypass |
| Permission/share violation on AlinaCoder staging/cache | preserve active target, clean safe staging, backoff, retry |
| Git/Ollama install not observed after launcher exits | re-detect inventory, clean owned transient state, retry |
| Ollama health/model pull/smoke incomplete | restart/re-detect Ollama, retry bootstrap; model pull remains resumable |
| unsupported Windows/hardware/model profile | fatal with clear blocker |
| allow-list/repository/source provenance violation | fatal immediately |
| user cancellation | stop immediately; preserve previous healthy state |

## Tests and release gates

New tests must prove:

- direct target truncation is impossible when staging copy fails;
- a locked target preserves the previous binary;
- stale staging and partial cache are cleaned safely;
- transient failure succeeds on a later automatic attempt without manual retry;
- fatal provenance failure is not retried indefinitely;
- an interrupted journal is resumable on the next setup run;
- successful recovery reports ready and allows launch;
- exhausted recovery reports error and leaves the previous target unchanged;
- existing rollback/provenance tests remain green;
- Windows packaging and visible-installer release gates remain green.

## Release acceptance

A release is publishable only when the full Python suite, installer-focused suite, packaging build, release verifier, and Windows smoke-install/repair workflow pass. The release evidence must include the self-healing tests and the final recovery journal schema version.
