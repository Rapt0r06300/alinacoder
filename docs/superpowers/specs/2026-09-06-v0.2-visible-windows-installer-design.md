# AlinaCoder v0.2 — Visible Windows Installer Design

## Context
The published `AlinaCoderSetup.exe` is technically capable of performing the LOT19 bootstrap, but the default double-click path is not a real end-user installer. It is packaged as a console executable, invokes the bootstrap immediately, emits only terminal text, can close immediately on error, provides no persistent diagnostic UI, no visible progress and no completion workflow. CI historically exercised only `--quiet`/CLI paths, so this UX failure was not covered by release acceptance.

This design makes the default double-click path a first-class Windows setup experience while preserving the already-validated CLI automation path.

## Product contract

### Default double-click behavior
Launching `AlinaCoderSetup.exe` with no command-line action opens one native AlinaCoder Setup window and **never opens a black console window**.

The window remains visible for the entire operation and exposes:
- product/version and install destination;
- detected machine summary (Windows, architecture, RAM, GPU/VRAM, free disk);
- selected local model and estimated model download size;
- an ordered checklist of phases;
- a determinate progress bar when byte totals are known and an indeterminate state otherwise;
- current action text;
- expandable live details/log output;
- `Cancel` while work is cancellable;
- persistent success/error state.

The user must be able to understand whether AlinaCoder is downloading, installing, validating, pulling a model, testing inference, creating shortcuts or completing.

### Installation phases
The GUI orchestrator exposes these phases explicitly:
1. `Préparation` — validate Windows and destination, create log directory.
2. `Analyse du PC` — detect RAM/VRAM/disk and choose the strongest fitting local model.
3. `Git` — preserve a compatible pre-existing Git or install verified official MinGit.
4. `Ollama` — preserve a compatible pre-existing Ollama or download/verify/install the official Ollama release.
5. `Modèle local` — pull the selected Ollama model with bounded retry/resume.
6. `Validation IA` — start Ollama, verify health and execute a real smoke inference.
7. `AlinaCoder` — copy the exact bundled application artifact into the per-user install directory.
8. `Intégration Windows` — create Start Menu/Desktop shortcuts and a per-user Apps & Features uninstall registration.
9. `Terminé` — show installed path, selected model, log location and a `Lancer AlinaCoder` action.

The actual bootstrap implementation remains deny-by-default. Visible progress never overrides security/provenance checks.

### Error behavior
Errors are first-class UI states, not terminal output.

On any failure:
- the window stays open;
- a human-readable headline is shown;
- the exact technical detail is retained in a scrollable diagnostics area;
- the persistent log path is shown;
- buttons `Réessayer`, `Copier le diagnostic`, `Ouvrir le dossier des logs` and `Fermer` are available as appropriate;
- `Réessayer` resumes from existing verified receipts/state rather than blindly reinstalling everything;
- no success shortcut/registry registration is created until bootstrap readiness is proven;
- the setup process returns non-zero only after the GUI closes or in explicit CLI mode.

Generic blockers alone are insufficient for diagnostics. The most recent underlying bootstrap exception must be recorded in the setup event/log stream.

### Progress and logging
Introduce structured setup events independent from Tkinter:

```python
@dataclass(frozen=True)
class SetupEvent:
    phase: str
    kind: str
    message: str
    detail: str = ""
    current: int | None = None
    total: int | None = None
```

The bootstrap/adapter accepts an optional event callback. It emits phase transitions, download byte progress, installer start/completion, model pull retry/status, health and smoke results.

Logs are written to `%LOCALAPPDATA%/AlinaCoder/logs/setup-YYYYMMDD-HHMMSS.log` and contain timestamp, phase, human message and technical detail. Secrets/tokens must never be written.

Download callbacks use the HTTP `Content-Length` when available. Model pull may remain indeterminate if Ollama does not provide a trustworthy total, but every retry/status must remain visible.

### Cancellation
Cancellation is cooperative and fail-safe:
- closing the window during active installation asks for confirmation;
- the UI sets a cancellation token checked between phases and during download loops;
- partial downloads/state remain resumable where safe;
- an external installer already executing is not force-killed in a way that can corrupt it unless a bounded timeout is exceeded;
- cancellation never writes `bootstrap_ready=true`.

### Windows integration
After successful bootstrap only:
- `AlinaCoder.exe` is installed under `%LOCALAPPDATA%/AlinaCoder`;
- a copy of the setup executable is kept as `%LOCALAPPDATA%/AlinaCoder/AlinaCoderSetup.exe` for repair/uninstall;
- Start Menu shortcut `AlinaCoder` is created;
- Desktop shortcut is created by default;
- HKCU Apps & Features entry is registered at `Software\\Microsoft\\Windows\\CurrentVersion\\Uninstall\\AlinaCoder` with DisplayName, DisplayVersion, InstallLocation, DisplayIcon and UninstallString;
- uninstall preserves pre-existing Git/Ollama/models by the existing ownership rules.

No administrator rights are required for AlinaCoder-owned files/registry. If an official prerequisite requires elevation, the GUI must explain it before Windows displays the elevation prompt.

### CLI compatibility
Existing automation remains supported:
- `--quiet`, `--repair`, `--upgrade`, `--rollback`, `--uninstall`, `--bootstrap-only`, `--offline`, `--model`, etc. continue to use the CLI engine and exit codes;
- no Tkinter UI is created when `--quiet` is supplied;
- CI keeps using explicit CLI flags for lifecycle coverage.

The no-argument path is the GUI path.

### Packaging
`AlinaCoderSetup.exe` must be built with PyInstaller `--windowed` so Windows does not create a console on double-click. Tkinter is included from the Python standard library. The application executable remains unchanged.

### Release acceptance changes
The release cannot be republished until the same SHA/artifact proves:
1. build script packages `AlinaCoderSetup` as `--windowed`;
2. no-argument entry point selects GUI mode;
3. GUI controller emits visible ordered phases from preparation through completion;
4. simulated failure leaves a durable error state and diagnostics rather than auto-close;
5. retry reruns the failed install using existing state;
6. persistent setup log is created;
7. success creates Windows integration metadata/shortcuts contract;
8. CLI `--quiet` LOT19 E2E remains green;
9. a packaged `--installer-ui-smoke` oracle validates the window/controller state machine without requiring interactive desktop automation;
10. final acceptance includes `visible_installer_e2e=true` bound to the same SHA and `AlinaCoderSetup.exe` digest.

## Audit findings to close
- Current setup is a console executable: critical UX defect.
- No default GUI: critical UX defect.
- Error console closes immediately: critical supportability defect.
- No visible installation/download/model progress: critical UX defect.
- CI tests only scripted quiet mode: release-gate defect.
- No persistent setup log/copy-diagnostics workflow: supportability defect.
- No retry/cancel experience: reliability/UX defect.
- No Start Menu/Desktop shortcuts: productization defect.
- No Apps & Features uninstall registration: productization defect.
- Setup executable is not copied into the install directory for maintenance: lifecycle UX defect.
- Underlying bootstrap exceptions can collapse to generic blockers: diagnostics defect.
- Success does not offer to launch AlinaCoder: onboarding defect.

## Done contract
The fix is Done only when a non-technical Windows user can download `AlinaCoderSetup.exe`, double-click it, observe every meaningful installation phase in one persistent graphical window, understand and recover from failures without a terminal, finish with a launchable AlinaCoder installation and standard Windows shortcuts/uninstall integration, while all previous LOT19/security/provider-fabric release gates remain green on the exact published SHA.
